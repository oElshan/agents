# Спринтовая модель доски — design proposal

> **Статус:** ✅ РЕАЛИЗОВАНО (все 5 рекомендаций приняты). Ядро — `commands/orchestrate.md`
> (scope=sprint по умолчанию), команда `commands/sprint.md`, поле доски `Sprint`.
> **Цель:** оркестратор работает только по утверждённому спринту и **никогда** не берёт из
> бэклога. Читает факт с доски (поле `Sprint == orchestrator.current_sprint`) каждый тик,
> ничего не додумывает; нет задач в спринте → ничего не делает.
> **Принятые решения (§10):** один Project + поле Sprint + views · спринт = dev-ready stories ·
> авто-баг→спринт / tech-debt→бэклог · single-select · carry-over → next.

---

## 1. Диагноз

Сейчас одно поле `Status` смешивает **планирование** (утверждён ли таск, в каком спринте) и
**исполнение** (где в конвейере). Оркестратор тянет прямо из колонки `Backlog` — то есть из
сырого потока идей. Нужно разделить эти два измерения.

## 2. Ключевая идея — два измерения

| Измерение | Поле | Кто ставит | Смысл |
|---|---|---|---|
| **Планирование** | `Sprint` (новое) | **человек** на планировании | утверждённый спринт задачи. Пусто = бэклог |
| **Исполнение** | `Status` (есть) | Team Lead | стадия конвейера |

**Единственное правило (и есть весь запрос):**
> Оркестратор обрабатывает только issue, где `Sprint == текущий спринт`. Issue без спринта
> (бэклог) для автопилота **невидимы**. «Утвердить в спринт» = проставить `Sprint=текущий` —
> это gate одобрения человеком.

Два измерения ортогональны: `Sprint` — какой батч, `Status` — где в конвейере.

## 3. Структура досок — один Project + поле Sprint + 2 view (рек.)

Одна физическая доска (Project), но два сохранённых view:
- **Backlog** — фильтр `Sprint = пусто` (весь интейк, все новые задачи).
- **Sprint** — фильтр `Sprint = current` (утверждённая работа; сюда смотрит оркестратор).

Почему так, а не два отдельных Project:
- вся текущая механика (`board.env`, хелперы `kb_*`, reconcile-workflow) работает без изменений — один `PROJECT_ID`;
- «перенос в спринт» = проставить поле, а не добавлять issue во второй проект + кросс-проектная автоматизация;
- это стандартный GitHub-воркфлоу спринтов.

«Отдельная доска бэклога» = отдельный view, физически та же доска.

## 4. Поле Sprint — single-select (рек.), не Iteration

⚠️ **Техническое ограничение:** GitHub **Iteration**-поле нельзя создать через API/CLI
(`gh project field-create` умеет только `TEXT|SINGLE_SELECT|DATE|NUMBER`) — только руками в UI.
Поэтому для автоматизируемого `/setup-board`:

- **`Sprint` = single-select** (рек.): опции `Sprint 1`, `Sprint 2`, … Пусто = бэклог.
  `/setup-board` создаёт поле; `/sprint new` дописывает опцию. Плюс — полностью ручной
  контроль «что и когда активно», что совпадает с «спринты, которые я утвердил».
- Альтернатива — **Iteration** (даты, `@current`, нативный burndown): создаётся один раз
  в UI, дальше `/sprint` управляет членством. Богаче, но не ставится авто-скриптом.

**Указатель текущего спринта** — в профиле: `orchestrator.current_sprint: "Sprint 1"`. Меняется
командой `/sprint activate`. Это и есть «какой спринт сейчас активен» под ручным контролем.

## 5. Что кладём в спринт — только dev-ready stories (рек.)

- Анализ и декомпозиция фич идут **в бэклоге вручную** (`/analyze` — human-triggered).
- В спринт человек утверждает уже **готовые к разработке stories**.
- Спринт = чистое исполнение (develop → deploy). Оркестратор **никогда не анализирует** —
  идеально совпадает с «не трогать бэклог».

> Одна и та же логика оркестратора поддержит и модель «фичи целиком» (тогда analysis-lead
> декомпозирует внутри спринта, а дочерние stories наследуют `Sprint=current`) — отличается
> только то, ЧТО кладёшь в спринт. Выбор — §8, вопрос 2.

Бэклог-view при этом показывает Sprint-пустые issue на ранних стадиях (`Backlog`/`Analysis`/
`Ready for Dev`) — там их и рефайнишь. Колонку Status `Backlog` **переименовывать не нужно**:
её смысл («на доске, ещё не проанализировано») совпадает с интейком. Клэша имён нет.

## 7. Команда `/sprint`

```
/sprint                      # доска текущего спринта: колонки, прогресс, что осталось
/sprint new "Sprint 2"       # создать спринт (дописать опцию поля Sprint)
/sprint activate "Sprint 2"  # сделать текущим (пишет orchestrator.current_sprint)
/sprint add #N #M …          # УТВЕРДИТЬ бэклог-issue в текущий спринт (Sprint=current) — gate одобрения
/sprint remove #N            # вернуть в бэклог (очистить Sprint)
/sprint plan                 # показать кандидатов из бэклога по приоритету → выбрать в спринт
/sprint close                # закрыть спринт: carry-over недоделанного (§ carry-over), сводка
```

`/sprint add` — единственный способ, которым работа попадает под автопилот. Это твой ручной
gate: пока не добавил в спринт — оркестратор задачу не видит.

## 8. Политики (нужен твой выбор — §Открытые решения)

**Роутинг авто-задач (рек.: «зависит от типа»).** Баг/регресс на задаче ТЕКУЩЕГО спринта →
наследует `Sprint=current` (блокирует цель спринта — чинить сейчас). Проактивный tech-debt от
G9 (через 72ч после прода) → бэклог (`Sprint` пусто) на триаж.

**Carry-over при `/sprint close` (рек.: «в следующий спринт»).** Недоделанные (не `Done`)
issue текущего спринта → переносятся в следующий спринт; альтернатива — назад в бэклог.
Спрашивать человека, дефолт — next.

## 9. Как это выглядит в работе

```
1. Новые задачи        → падают в Backlog-view (Sprint пусто). Оркестратор их не трогает.
2. Рефайнинг (вручную) → /analyze фич → stories, всё ещё Sprint пусто.
3. Планирование        → /sprint add #101 #102 #103  (Sprint = "Sprint 2")  ← твой gate
4. Активация           → /sprint activate "Sprint 2"
5. Исполнение          → /orchestrate  → крутит ТОЛЬКО #101 #102 #103 до Done
6. Закрытие            → /sprint close → недоделанное → в Sprint 3
```
