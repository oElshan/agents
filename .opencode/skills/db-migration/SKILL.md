# Миграции БД

Инструмент из `stack.data.migration_tool` профиля.

## Абсолютный запрет

Применённую миграцию (файл уже есть в базовой ветке) не меняют никогда: ни SQL, ни
комментарий, ни пробел. Flyway и Liquibase хранят checksum применённых миграций, правка
ломает валидацию и роняет сервис при старте. Оркестратор проверяет это на G4 командой
`git diff --name-status --diff-filter=MDR <base>...<story> -- <paths.migrations>`.

Нужно изменить схему: новая миграция. Задача требует поправить текст старой миграции:
это вне scope, напиши об этом в отчёте.

## Новая миграция

- Flyway: `V<max+1>__<snake_case_описание>.sql` в каталоге миграций модуля. `<max>`
  определи по существующим файлам (`ls … | sort -V | tail -1`), учитывая формат версий
  проекта (`V42__`, `V2024_10_16_1__`).
- Liquibase: новый changeset (`id` по конвенции проекта, `author`), подключённый в master
  changelog.
- Rollback: Flyway `U<версия>__…sql` (если проект использует undo) или SQL отката в arch doc;
  Liquibase блок `<rollback>`. Невозможно: `forward-only: <причина>` в SDC 4.

## Совместимость

Схема и код живут вместе на время rolling update:
1. **expand**: добавить колонку или таблицу nullable или с default, старый код продолжает работать;
2. **migrate**: код пишет в новое, данные переносятся;
3. **contract**: удаление старого отдельной миграцией в следующем релизе.

Переименование и удаление колонки за один шаг запрещены.

## Блокировки и объём

- PostgreSQL: индекс на большой таблице `CREATE INDEX CONCURRENTLY` (вне транзакции, в
  Flyway отдельная миграция с `executeInTransaction=false` или конфигом проекта).
- `ALTER TABLE … ADD COLUMN … DEFAULT` на больших таблицах проверь на версии СУБД.
- Перенос данных пачками, без загрузки таблицы в память.

## Индексы

Новый `findBy…` или `@Query` по колонке без индекса: индекс в той же миграции.
