# Spec фичи

Шаблон: `spec-template.md` рядом с этим файлом. Файл spec: `docs/specs/<F>-<slug>.md`, где
`<slug>` из 2–4 слов латиницей через дефис.

## Критерии приёмки

- Один AC = один сценарий: один Given, один When, один Then. Если в Then два независимых
  результата («и также»), это два AC.
- ID `AC-<F>-NN` по порядку с `01`, уникальны в spec, после утверждения не переиспользуются
  и не перенумеровываются. Удалённый AC помечается `~~AC-12-04~~ удалён: <причина>`.
- У каждого AC строка `Проверка:`
  - `stand`: проверяется запросом к живой системе (по умолчанию для API и UI-сценариев);
  - `integration`: интеграционным тестом (Testcontainers), когда сценарий нельзя вызвать
    снаружи (consumer сообщения, scheduled job);
  - `unit`: только чистые вычисления без I/O.
- Покрой для API: успех, 401 без токена (если есть auth), 403 для чужой роли (если RBAC),
  404, 400 на невалидный ввод, границы пагинации (если список).
- Then описывает наблюдаемый результат: код ответа, тело, состояние, которое видно через
  API. «Работает корректно» не годится.

## Нефункциональные требования

- Производительность числами: p95, p99, RPS, объём. Без чисел раздел не принимается.
- Большие объёмы не обрабатываются в памяти процесса. Ключи и уникальные значения
  генерирует внешний механизм: СУБД, генератор ID, брокер.
- Для каждой изменяемой операции: модель согласованности и идемпотентность.
- Решение работает в нескольких экземплярах сервиса.

## Декомпозиция

Story = наименьший кусок, который можно смёржить и проверить его собственными AC.

- **INVEST.** Независимая (иначе зависимость в колонке «Зависит от»), ценная, оцениваемая,
  маленькая, проверяемая.
- **Размер:** xs (< 2 ч), s (≈ 4 ч), m (1–2 дня). Больше 3 дней: дели. Размер l бывает
  только у фичи.
- **AC:** у story один или несколько AC из spec. Каждый AC фичи закрывает хотя бы одна story.
- **Зависимости** только там, где без другой story код не соберётся или AC не проверить.
  Циклы запрещены.
- **Не дробить механически.** Нет правила «одна story на слой» и запрета на « и » в
  названии. Если backend и frontend одного сценария вместе укладываются в m, это одна story.
- **Микросервисы** (`topology.type: microservices`): в названии или описании story указаны
  затронутые сервисы.

### Frontend

Фреймворк приложения из `stack.frontend[].framework`.

- **React (FSD):** story соответствует пользовательскому сценарию или слайсу. Если сценарий
  требует новой сущности (`entities/<x>`) и она нужна другим сценариям, выдели её в
  отдельную story и поставь зависимость. Запрещены AC с прямым HTTP из `features/` или
  `widgets/`: запросы только через `shared/api` или `entities/<x>/api`. Подробности: skill
  `react-fsd`.
- **Angular:** story = feature-область (`features/<area>`) или самостоятельный компонент или
  сервис внутри неё. Нужный core-сервис должен быть готов (зависимость). Подробности: skill
  `angular`.

## SDC

Загрузи skill `sdc`: когда блок обязателен, как заполнять слоты, когда допустимо `SDC: N/A`.

## budget.md и ownership-map.md

- Новая таблица, очередь, topic, префикс endpoint: строка в `docs/arch/ownership-map.md`.
- Новый модуль, сервис, внешняя интеграция, очередь, БД: счётчик и строка журнала в
  `docs/arch/budget.md`. Если событие из таблицы порогов требует ADR, отметь в слоте
  OWNERSHIP «нужен ADR» — его напишет architect.
- Оба файла коммитятся вместе со spec.

## Чек-лист перед коммитом

- все разделы шаблона заполнены, `{{…}}` не осталось;
- `grep -oE '^### AC-<F>-[0-9]+' <spec> | sort | uniq -d` пусто;
- у каждого AC есть строка `Проверка:`;
- каждый AC встречается в таблице «Декомпозиция»;
- SDC заполнен или `SDC: N/A — <причина>`.
