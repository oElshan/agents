# Руководство оператора

Продуктовое описание и быстрый старт: [README](../README.md).
Этот документ описывает управление подключённой командой агентов.

## Команды

| Команда | Назначение |
|---|---|
| `/setup` | Подготовить или обновить профиль проекта. |
| `/feature <описание>` | Создать фичу в Backlog. |
| `/correction <story-id> <описание>` | Создать отдельную story изменения поведения с correction-спекой. |
| `/sprint add <id>` | Взять задачу в работу. |
| `/sprint remove <id>` | Вернуть задачу из Sprint в Backlog. |
| `/orchestrate` | Вести задачи до остановки или запроса решения. |
| `/orchestrate once` | Выполнить один шаг. |
| `/orchestrate <id>` | Работать с одной задачей или фичей. |
| `/orchestrate dry-run` | Показать следующий шаг без изменений. |
| `/approve <id>` | Утвердить проверенный снимок документов. |
| `/board` | Показать доску. |
| `/unpark <id>` | Продолжить задачу после устранения причины остановки. |
| `/stage off deploy` | Остановить начало новых деплоев. Очередь сохраняется. |
| `/stage on deploy` | Снять паузу деплоя. |
| `/deploy` | Развернуть готовый пакет на staging. |
| `/sync setup`, `/sync` | Подключить GitHub и синхронизировать доску. |
| `/analyze`, `/develop`, `/test`, `/e2e` | Отдельные операции; аргументы описаны в файлах команд. |

Полные инструкции: [commands](../.opencode/commands).

## Файлы проекта

| Путь | Содержимое |
|---|---|
| `.opencode/` | Поставляемые агенты, команды, skills и проверки. |
| `opencode.json` | Настройки моделей и провайдеров проекта. |
| `.agents/profile.md` | Команды сборки, тестов, стенда и пороги качества. |
| `AGENTS.md` | Контекст проекта для агентов. |
| `.agents/board/` | Карточки и паузы стадий, обычно вне Git. |
| `.agents/cache/` | Рабочие данные и настройки синхронизации, обычно вне Git. |
| `docs/specs/`, `docs/arch/`, `docs/qa/` | Требования, архитектура и результаты QA. |

Смена ветки не переносит и не резервирует игнорируемую доску. Сохраняйте её отдельно.
Запускайте оркестратор в отдельном клоне. Worktree помогает разделить работу,
но не ограничивает доступ процесса к файлам компьютера.

## Процесс и остановки

Фича получает ветку `feature/<id>-<slug>`. Каждая задача разработки получает ветку
`story/<id>-<slug>`. После ревью и QA оркестратор сливает задачу в feature-ветку.
Перед PR тестировщик проверяет все критерии фичи.

| Результат | Действие |
|---|---|
| PASS | Перейти к следующему пункту проверки. |
| FAIL | Передать подтверждённый дефект на доработку. |
| ERROR | Остановиться: нет пригодного результата проверки. |
| NOT_VERIFIED | Остановиться: нужный способ проверки недоступен. |
| REVIEW_REQUIRED | Новые тесты должны пройти G4 и ревью, затем новый QA. |

По умолчанию после трёх неудачных попыток задача ждёт человека.
Причина находится в `parked_reason`, детали — в журнале карточки.
Пауза стадии не заменяет успешное прохождение этой стадии.

Фича имеет master и минимум одну story с собственными spec, AC, снимком утверждения и QA.
Утверждённые specs не редактируются: изменение поведения создаёт correction дочерней story.
`corrects` и `supersedes` сохраняют связь с прежними требованиями. Текущая регрессия учитывает
только интегрированные corrections. Изменение профиля/архитектуры/правил требует G2 и approve,
но не разрешает переписывать старые specs.

Независимые stories идут в отдельных worktree. `orchestrator.parallel_stories: 2` задаёт
лимит; у старых профилей без поля используется 1 до `/setup`. Зависимости, внешние blockers,
общие файлы и ресурсы ограничивают параллельность. Merge выполняет один orchestrator;
если база сдвинулась, story повторяет ревью и QA на обновлённой базе.

[Формат графа и миграция старых спек](../.opencode/skills/write-spec/references/spec-graph.md).
Старый монолитный файл сохраняется: новые story-файлы получают ссылки на источник и карту AC.
Не включайте новый процесс в середине активного запуска без проверки новых контрактов.

Полный процесс: [quality-gates](../.opencode/skills/quality-gates/SKILL.md).

## Модели и качество

Настройки моделей держите в корневом `opencode.json`, отдельно от поставляемого фреймворка.
Выберите доступные ID через `opencode models`. Ниже схема, а не готовые ID моделей:

```json
{
  "model": "<provider>/<default-model>",
  "agents": {
    "analyst": { "model": "<provider>/<analysis-model>" },
    "developer": { "model": "<provider>/<coding-model>" },
    "security-reviewer": { "model": "<provider>/<review-model>" },
    "tester": { "model": "<provider>/<testing-model>" }
  }
}
```

Ключ роли совпадает с именем файла в `.opencode/agents/` без `.md`.
Подключите всех используемых провайдеров. Каждая модель должна поддерживать инструменты.
Код и вывод команд передаются провайдерам, которые используются в запуске.

Проверка принятой конфигурации:

```bash
opencode debug config
opencode debug agents
```

Загрузка конфигурации не доказывает, что агент выполнил задачу на ожидаемой модели.
Проверьте фактическую модель по сессии после пилота. Не выбирайте модель только по цене:
сравните правильность результата, число доработок и стоимость принятого изменения.
Для локальных моделей согласуйте реальный размер контекста сервера с настройкой OpenCode.

Пороги и команды задаются в `.agents/profile.md`. Фрагмент для Maven:

```yaml
commands:
  backend:
    build: "./mvnw -q package -DskipTests"
    test: "./mvnw test"
    coverage: "./mvnw clean verify"
    coverage_sources:
      - root: src/main/java
        report: target/site/jacoco/jacoco.xml
quality:
  unit_coverage_min: 95
  hotfix_coverage_min: 50
  fix_loop_max: 3
```

JaCoCo должен быть настроен в сборке. Для каждого модуля укажите его отчёт.
Пустая обязательная команда блокирует проверку. Команды профиля выполняются с правами
пользователя; проверьте их перед запуском.

[Полный шаблон профиля](../.opencode/skills/project-setup/templates/profile.md) ·
[Исполняемые проверки и переход на v2](../.opencode/lib/README.md)

## GitHub и staging

Для зеркала доски задайте `tracker.mode: github`, подключите `gh` с правом `project`
и выполните `/sync setup`. Источник состояния — локальные карточки.
Из GitHub принимаются новые задачи и решения Backlog ↔ Sprint.
Комментарии issue не разрешают агенту утверждать требования или обходить проверки.

После неопределённого результата создания issue система должна проверить маркер карточки.
Не очищайте `github.create_pending` без проверки GitHub: запрос мог создать issue до тайм-аута.
[Правила синхронизации](../.opencode/skills/github-sync/SKILL.md).

Staging включается командой `commands.deploy.staging`. В v2 также нужны
`prepare_artifact`, `observe_artifact`, `status` и smoke. Подготовка возвращает manifest
с SHA кода и digest артефактов. Деплой использует эти digest. Проверка получает
фактические значения из staging. DevOps не меняет файлы и не создаёт новую сборку.
[Формат manifest](../.opencode/lib/README.md#артефакты-деплоя).

## Другие способы подключения

Subtree — основной способ. Он сохраняет фреймворк в репозитории проекта и позволяет
сливать локальные изменения при обновлении. Используйте `--squash` и при add, и при pull.

Для submodule с точной версией:

```bash
git submodule add -b dist https://github.com/oElshan/agents.git .opencode
git -C .opencode fetch origin --tags
git -C .opencode checkout v2.1.0
git add .gitmodules .opencode
git commit -m "chore: connect agent team v2.1.0"
```

Для обновления существующего submodule выполните fetch, checkout нужного тега и commit
указателя в родительском проекте. Другие разработчики выполняют `git submodule update --init`.
Эти команды подключения выполняет человек: агентам `git -C` запрещён политикой.

Если `.opencode/` уже существует без subtree или submodule, сначала сохраните его содержимое.
Не удаляйте локальные настройки вслепую. Согласуйте имена агентов и команд с поставляемыми.
Пользовательский skill требует разрешения в `policies` конфигурации фреймворка.

## Диагностика и ограничения

| Симптом | Что проверить |
|---|---|
| Subtree сообщает об изменённом дереве | Сохранены ли изменения в Git. Для нового проекта нужен первый коммит. |
| Список агентов пуст сразу после обновления | Повторите диагностику через несколько секунд. При повторной ошибке проверьте frontmatter. |
| Покрытие заблокировано | Есть ли XML, обновляет ли его команда, заданы ли корни всех модулей. |
| После обновления требуется утверждение | Это ожидаемо: изменились профиль или правила, входящие в снимок. |
| Задача остановлена | Прочитайте `parked_reason` и журнал. Устраните причину перед `/unpark`. |

Политики OpenCode и запрет инструмента редактирования не создают файловую песочницу.
Shell и дочерние процессы могут писать файлы. Чистый Git не подтверждает сохранность
игнорируемого состояния. Вызов проверок пока обеспечивает инструкция оркестратора.
Не запускайте несколько оркестраторов над одной доской.

Браузерные тесты не входят автоматически в каждую задачу. Полный цикл GitHub sync,
staging и маршрутизация разных моделей требуют проверки на вашем проекте.
