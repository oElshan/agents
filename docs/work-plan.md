## Правила каждой итерации

1. Записать одну гипотезу: какую проблему устраняем и какой результат ожидаем.
2. Зафиксировать сравниваемые версии, условия, предел затрат и критерии принятия.
3. Сначала воспроизвести проблему. Для исправления дефекта добавить проверку,
   которая различает ошибочное и правильное поведение.
4. Внести одно изменение. Смену модели, инструкций и состава ролей проверять отдельно.
5. Повторить затронутые задачи и исходный набор. Сравнивать с предыдущей принятой
   версией; сохранять также первоначальные показатели W01.
6. Записать решение: принять, доработать или откатить, с результатами и ограничениями.

Пять задач по три попытки — стартовый объём пилота, а не доказательство надёжности
для любых проектов. При неоднозначном результате нужны дополнительные попытки.
Провалы среды и ошибки проверки учитывать отдельно от ошибок агента; не скрывать их
и не заменять неудачные попытки успешными без записи.

Новые сценарии добавлять в набор с отдельной версией. Не менять задним числом условия
и критерии, чтобы улучшить оценку уже выполненного прогона. Реальные дефекты превращать
в постоянные проверки. Сложные новые задачи учитывать отдельно от уже освоенных.

### Что измеряем

| Показатель | Правило учёта |
|---|---|
| Принятие без исправлений человеком | Число принятых результатов / число завершённых попыток; внутренние доработки агентов показывать отдельно |
| Повторяемость | Результаты каждой из трёх попыток по каждой задаче; отдельно задачи, успешные во всех попытках |
| Время человека | Минуты на контроль, разбор ошибок и исправления; измерять явно, не выводить из токенов |
| Время выполнения | От старта до результата; отдельно ожидание человека и простой внешних систем |
| Стоимость | Модели, повторные попытки и незавершённая работа; общие затраты и стоимость принятого изменения |
| Качество проверок | Пропущенные дефекты, ложные замечания и ложные PASS/FAIL |

Недоступные значения отмечать как «не измерено». Если цена оценочная, сохранять
источник тарифа и дату. Снижение расходов само по себе не оправдывает ухудшение качества.
Ложный PASS, недопустимое изменение или нарушение доступа блокируют принятие итерации.

### Что сохраняем о попытке

- ID задачи и попытки; исходный и итоговый SHA проекта; версия агентской системы.
- Версия OpenCode, фактические модели по ролям, настройки и версии инструкций.
- Команды, зависимости и значимые параметры окружения; версии использованных документов.
- Результаты инструментов и проверок, изменения кода, причины остановок и повторов.
- Время, расход токенов, стоимость и оценка человеком, если доступны.
- Итог и ссылки на проверяемые артефакты; состояние внешних операций, если они выполнялись.

Журналы не должны содержать секреты. Контрольные тесты и эталонные результаты хранить
вне области записи исполнителя. Каждая попытка начинается с одинакового исходного
состояния и не получает решение предыдущей попытки. Worktree разделяет рабочие файлы,
но сам по себе не обеспечивает изоляцию прав и очистку всех внешних ресурсов.

контроль доступа и устойчивое состояние — предварительное условие, а не необязательная оптимизация.

## W03 — эффективность с учётом проекта

Состав ролей определяется задачей, риском, компонентами и качеством существующих тестов.
Каждый вариант — гипотеза для сравнения, а не уже принятое изменение процесса.

| Ситуация | Проверяемый вариант |
|---|---|
| Маленькое исправление с ясными требованиями | Разработчик, применимое ревью и целевые проверки |
| Новая бизнес-функция | Аналитик, архитектура при необходимости, реализация, ревью и приёмка |
| Legacy с недостаточными тестами | Исследование поведения и фиксирующие его тесты перед изменением |
| UI | Браузерная проверка пользовательских сценариев в обязательном маршруте |
| Микросервисы | Контрактные тесты, совместимость потребителей и сбои зависимостей |
| Высокая нагрузка | Профилирование и нагрузочные сценарии с измеримыми ограничениями |
| Доступ, критичные данные и миграции | Усиленные проверки, испытание отката и предусмотренные решения человека |

Проверять отдельно сокращение контекста роли, устранение ненужных передач работы,
состав проверяющих и выбор модели. Резервная модель сохраняет требования качества и доступа.
Повторно использовать результат проверки можно только при совпадении её значимых входов.
Независимые проверки можно распараллеливать; параллельную разработку нескольких задач
отложить до появления отдельных сред, контроля зависимостей и состояния.

## W04–W05 — знания, трекеры и GitLab

Подтверждённый пользователем набор: **Confluence, Jira, GitLab, YouTrack**.
Порядок: Confluence на чтение → Jira + GitLab → адаптер YouTrack.
Для каждого проекта выбирать один основной трекер; Jira и YouTrack не должны
конкурировать за управление одной задачей.

### Границы ответственности

| Данные | Основной источник |
|---|---|
| Бизнес-задача, приоритет, ответственный, решение взять в работу | Выбранный трекер |
| Внутренние этапы, попытки, ошибки и результаты агентов | Состояние управляющего модуля |
| Код, MR и результаты CI | GitLab |
| Общие бизнес-правила | Confluence или выбранная база знаний |
| Утверждённая спецификация конкретного изменения | Версионируемый документ со ссылками на исходные требования |

MCP/API предоставляют доступ к сервисам. Они сами по себе не реализуют процесс,
восстановление после сбоя и защиту от дублей. Облачные и внутренние установки могут
требовать разных адаптеров и способов авторизации; версии уточнить перед подключением.

Для знаний:

- Начать с поиска источников и чтения нужных разделов, без собственного векторного
  хранилища. Добавлять индекс только при измеренной необходимости.
- Сохранять ID, ссылку, версию или дату документа и связь с требованием.
- Проверять актуальность и противоречия; при отсутствии данных не выдумывать правило.
- Применять права пользователя и проекта. Текст документов и задач считать данными,
  а не командами, изменяющими правила работы агента.
- Добавить сценарии с устаревшими документами, отсутствующим ответом и закрытым доступом.

Для трекеров и GitLab:

- Выделить общий интерфейс операций и адаптеры Jira, YouTrack, GitLab; сохранить
  совместимость существующих local/GitHub режимов или явно описать миграцию.
- Изменения внешних систем выполнять через контролируемый путь; не выдавать каждой
  роли свободную запись во все сервисы.
- Хранить связи task ID → run ID → commit SHA → MR → CI → при необходимости release.
- Сопоставлять статусы с процессом команды; внутренние этапы не обязаны становиться
  отдельными колонками внешней доски. Draft MR не означает завершение поставки.
- Сохранять очередь исходящих операций, идентификаторы и результат отправки.
  После тайм-аута проверять результат перед повтором; учитывать изменения человеком.
- Проверить недоступность сервиса, потерянный ответ, перезапуск, повторное событие,
  конфликт правок и отказ в доступе. Не создавать дубли задач и комментариев.

Целевой сценарий: **задача Jira/YouTrack → требования Confluence → изменение GitLab →
проверенный draft MR → отчёт в исходной задаче**. Production остаётся вне автоматизации.
Текущие решения человека о начале работы, утверждении требований и слиянии сохраняются,
пока отдельная итерация явно не изменит соответствующее правило.
