# Параллельные stories

Один orchestrator владеет доской, выдачей ID, блокировками и слиянием. Несколько orchestrator
над одной доской запрещены. `orchestrator.parallel_stories` — предел одновременно активных
stories (по умолчанию 2; 1 для последовательного режима). Ревьюеры одной story могут читать
её worktree параллельно; developer и tester в одном worktree одновременно не работают.

## Выбор задач

1. Прочитай [граф спецификаций](../write-spec/references/spec-graph.md), доску и stage pauses.
   Сначала отбери допущенные карточки (scope, Sprint/Ready for Dev, approve, stage, parked).
   Передай их spec ID через повторяемый `--candidate`; если их нет, новую волну не запускай.
   Из `spec-plan` получи ready с учётом всех активных spec ID, integrated prerequisites и
   resolved blockers. Для нескольких фич учитывай конфликты межфичевых ресурсов и путей.
   Legacy/standalone bug/tech-debt без spec/v1 запускай эксклюзивно: неизвестную область
   записи нельзя считать независимой. Общие build/test ресурсы учитываются на всех стадиях.
2. Из ready оставь карточки в scope запуска, Ready for Dev/Sprint, с утверждёнными контрактами,
   без parked/excluded. Результаты зависимостей должны уже входить в конкретную integration base.
   Передавай candidate в порядке priority, затем card ID; spec-plan сохраняет этот порядок.
   Без candidate используется порядок spec ID. Допускается запуск меньшего набора. Не обходи заблокированные элементы ради заполнения слотов.
3. Запиши резервирование в карточках ДО запуска: `worktree`, `base_commit`, `resources`,
   `writes`, `reads`, `execution: reserved`. Новую выдачу сериализуй. Ресурсы — из утверждённой
   spec, не из пересказа карточки. Общие профильные ресурсы учитываются дополнительно.
4. Незакрытая функциональная зависимость запрещает старт; пересечение writes/writes,
   writes/reads или resources сериализует задачи. Пустое описание области — блокировка,
   не разрешение параллелизма. Независимые проверки читай параллельно, записи в доску — по одной.

## Worktree и запуск

Основной checkout — только анализ/интеграция. Для каждой готовой story:

```bash
git worktree add -b story/<S>-<slug> .agents/worktrees/<S> <base>
```

Корень `.agents/worktrees/` исключён из Git через `/setup`. Существующий worktree не
пересоздавай: проверь `git worktree list --porcelain`, ветку, HEAD и чистоту. Сохрани абсолютный
путь в карточку. Игнорируемые `.agents/board`/cache не появляются в новом worktree сами.
Передай абсолютный путь к центральной карточке для чтения, а cache создай отдельный в worktree.
Профиль, AGENTS.md, specs, arch и framework должны быть закоммичены и доступны в worktree;
не копируй секреты и локальные незакоммиченные настройки.

Каждый task получает абсолютный cwd, ветку, base SHA, spec ID, spec/master/arch, AC,
writes/reads/resources, QA path. Каждый инструмент должен явно работать внутри этого cwd:
команды — с рабочим каталогом инструмента или `cd <worktree>` в той же shell-команде;
файловые операции — по абсолютным путям. Перед работой агент подтверждает
`git rev-parse --show-toplevel`, `git branch --show-current`, `git rev-parse HEAD`.
`git -C` остаётся запрещён существующей политикой. Не меняй cwd главного checkout ради агента.

Если runtime не поддерживает независимый cwd/адресацию инструментов, работай последовательно
и сообщи ограничение. Не запускай двух писателей в общем checkout. При корректной изоляции
отправляй независимые task одновременно и обрабатывай их отчёты по мере завершения.
После перезапуска восстанови execution по реальным worktrees/запускам; неизвестный живой
процесс не объявляй завершённым. Парковка сама по себе не освобождает ресурс: сначала
дождись завершения агента и погаси принадлежащий ему стенд.

## Сборка и QA

QA story: `docs/qa/F<F>/S<N>.md`; correction: `docs/qa/F<F>/S<N>-C<K>.md`.
Feature regression: `docs/qa/F<F>/regression.md` (единственный интегратор).
Build outputs и cache локальны worktree. Общие БД, порты, docker compose project, внешние
очереди и staging не изолируются Git. По умолчанию держи исключительную блокировку
`stand:shared` на время команд стенда/integration и `deploy:staging` на время деплоя.
Если профиль `orchestrator.isolated_test_env: true`, `/setup` должен подтвердить, что команды
действительно используют уникальные порты/БД/compose names для worktree. Иначе QA/интеграционные
сборки идут по одной, даже когда разработка параллельна. Стенд останавливает только владелец.

Developer без stand-lock заканчивает фазу правок перед общей тестовой командой и возвращает
`WAIT_RESOURCE: stand:shared` с HEAD/перечнем отложенных команд. Это не FAIL/BLOCKED human:
orchestrator оставляет In Development, execution: waiting, не увеличивает attempts. Когда
ресурс освободится, выдаёт lock и возобновляет того же developer для тестов/коммита. G4 и
tester также получают lock до общей команды; права на этот ресурс передаются явно в task.

## Интеграция

G4 включает `spec-scope`; выход за writes паркует story, новые общие изменения нельзя
молча включить в коммит. Незавершённый черновик можно уточнить до approve; для утверждённого
контракта изменение scope оформляй correction/новой story и заново планируй затронутую работу.

Слияния в feature/default target всегда по одному. Перед G6 сравни фактический HEAD базы с
`base_commit`. База сдвинулась: в worktree story orchestrator вливает её, обновляет base_commit,
очищает review/coverage/QA и повторяет G4 → G5 → G6 даже при чистом merge. Конфликты разрешает
developer в этой story; остальные независимые worktrees продолжают работу. Нельзя использовать
старый PASS после интеграционных изменений. Если base не сдвинулась, выполняй обычный G6.

После G6 интегратор проверяет, что база по-прежнему та же, вливает story, записывает
`integrated_commit` и проверяет ancestor. Только теперь освобождает блокировки и делает
зависимые задачи доступными. Done/staging не подменяет этот факт. Для correction выпущенной
фичи integration base — её отдельная ветка изменения, и PR завершает этот цикл.

Удалять worktree только после окончания всех задач и проверки чистоты, обычным
`git worktree remove <path>`, без force. Затем можно `git branch -d <story>` для смёрженной
ветки. При ошибке сохрани worktree и причину; чужие изменения не удаляй.
