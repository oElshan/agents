# Проверка AC на стенде

Вердикт по AC выносится по факту: код ответа, тело, состояние через API, лог, вывод
тест-раннера. «Похоже, работает» не считается.

## 1. Тест-кейсы из AC

На каждый AC минимум:
- основной сценарий;
- ошибка или граница (нет объекта → 404, невалидный ввод → 400, пустые поля, лимиты);
- права, если есть auth: без токена 401, чужая роль 403;
- negative: неверный ввод → ожидаемая ошибка с понятным сообщением.

Дополнительно:
- микросервисы: зависимость недоступна → graceful degradation (SDC 5); повтор запроса или
  события → нет дубля (SDC 2);
- high-load: запрос без пагинации ограничен, cap на page size, последняя страница корректна;
- слот NOT-DOING (SDC 8): исключённое не реализовано.

ID тест-кейсов `TC-<F>-NNN`, у каждого ссылка на AC.

## 2. Сборка

```bash
git rev-parse HEAD                      # равен SHA из задачи
<commands.backend.build>                # сломано → вердикт FAIL, стенд не поднимаем
```

## 3. Стенд

Выбери первый доступный уровень и запиши его в отчёт. Если у всех AC задачи `Проверка: unit`,
стенд не нужен: уровень C.

**A. Живое окружение**, если задан `commands.local_env.up`:
```bash
<commands.local_env.up>
# ждём health каждого сервиса из topology.services[] (до ~120 с)
for i in $(seq 1 24); do curl -sf http://localhost:<port><health> && break; sleep 5; done
```
Сервис не поднялся healthy: это дефект, вердикт FAIL с выдержкой логов
(`docker compose logs --tail=80 <service>`).

**B. Testcontainers**, если `local_env.up` пуст, но есть `commands.backend.integration_test`.
AC проверяются интеграционными тестами с реальными зависимостями. AC без теста: допиши
интеграционный тест в тестовом каталоге, запусти, приложи вывод.

**C. Без стенда**: нет ни окружения, ни интеграционных тестов, или нет Docker. Прогони
автотесты. AC с `Проверка: unit` проверяются тестами. AC с `Проверка: stand` или
`integration` получают `NOT_VERIFIED` с причиной. Чтение кода AC не подтверждает.

## 4. Прогон AC

Уровень A, пример:
```bash
TOKEN=$(curl -s -X POST "$BASE/auth/login" -H 'Content-Type: application/json' -d '{…}' | jq -r .token)
curl -s -o .agents/cache/resp.json -w '%{http_code}\n' "$BASE/<endpoint>" -H "Authorization: Bearer $TOKEN"
head -c 400 .agents/cache/resp.json
```
- создание проверяй последующим GET через API, не прямым SQL;
- права: без токена и с токеном чужой роли;
- для каждого сценария сохрани код ответа и характерный фрагмент тела или лога.

Секреты и токены в отчёт не попадают: маскируй (`eyJ…`).

## 5. Автотесты

Всегда, на любом уровне:
```bash
<commands.backend.test>                 # microservices: test_one_service по затронутым
```
Счётчики и итог из вывода. Цифрам из отчёта developer не доверяй.

## 6. Вердикт

| AC | Условие |
|---|---|
| PASS | все его тест-кейсы прошли, есть evidence |
| FAIL | хотя бы один тест-кейс не прошёл |
| NOT_VERIFIED | требуемый способ проверки недоступен |

Story: `PASS`, если все AC PASS, автотесты и сборка SUCCESS. `FAIL`, если есть FAIL или
упали сборка, тесты. Иначе `NOT_VERIFIED`.

У каждого FAIL: severity (critical: утечка данных или сломан основной поток; high: не
работает основной сценарий; medium: граница или второстепенный сценарий; low: косметика),
repro (команда стенда, запрос, роль), expected из AC, actual с evidence. Один корень на
несколько AC: один пункт с перечнем AC.

## 7. QA-документ

`docs/qa/<F>-<slug>.md` (у самостоятельной задачи `docs/qa/<id>-<slug>.md`). Документ живой:
при каждом прогоне обновляются «Последний прогон» и результаты.

```markdown
# QA: <F> — <название>

Spec: docs/specs/<F>-<slug>.md
Последний прогон: <дата> · story <S> · SHA <sha> · стенд A | B | C · вердикт PASS | FAIL | NOT_VERIFIED

## TC-<F>-001: <сценарий>
AC: AC-<F>-01 · Приоритет: Critical | High | Medium · Тип: API | UI | RBAC | Edge
| # | Действие | Данные | Ожидаем |
|---|---|---|---|
| 1 | POST /api/v1/… | {…} | 201 + объект |
Результат: `201 {"id":42,…}` · PASS · <дата>
```

Закоммить: `docs(<S>): QA — <pass>/<total> AC`.

## 8. Погасить стенд

Уровень A: `<commands.local_env.down>`.

## Режим regression

Оркестратор запускает его на HEAD feature-ветки перед PR. Прогони все AC фичи (не только
одной story) теми же правилами. Сломанный AC, который раньше был PASS, в отчёте отдельной
секцией `REGRESSION` с id story, AC и evidence.
