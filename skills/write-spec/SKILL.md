# Дерево спецификаций

Сначала прочитай [формат и жизненный цикл](references/spec-graph.md). Он общий для analyst,
architect и orchestrator. Храни Markdown в Git; корень репозитория можно открыть как vault.

## Новая фича

1. Создай `docs/specs/F<F>-<slug>/master.md` по [spec-template.md](spec-template.md).
   Master задаёт цель, scope, общие ограничения, FR и ссылки на stories. Это не задача кода.
2. Всегда создай хотя бы одну story, даже для маленькой фичи. Каждая story — минимальный
   проверяемый функционал с собственным файлом, FR, AC, SDC, планом проверки и отката.
   Шаблон: [story-template.md](story-template.md). AC существуют только в story/correction.
3. Проведи декомпозицию по INVEST: xs (<2 ч), s (~4 ч), m (1–2 дня); больше 3 дней — дели.
   Не дели механически по слоям. Backend и frontend одного сценария могут быть одной story.
   Каждый FR master покрыт ссылкой на story, каждая story связана с целью master.
4. В `depends_on` укажи только обязательные предварительные результаты. В `blockers` —
   внешние условия с устойчивыми ключами. В `writes`/`reads` — точные файлы или каталоги,
   в `resources` — общие API, DTO, таблицы, миграционные master, порты/стенды.
   Для конфликта файлов без функциональной зависимости достаточно сериализации ресурсов.
5. Общий контракт сначала закрепи в master/архитектуре. Если нужна его реализация,
   выдели story-предпосылку. Architect проверяет зависимости и возможные конфликты.
6. Закоммить документы. Выполни `spec-graph` из справочника. Передай orchestrator карту
   spec ID → путь → AC → зависимости/блокеры; номера карточек он назначит после утверждения.

## Изменение поведения

После утверждения исходные spec-файлы неизменяемы, включая frontmatter, AC и ссылки.
После реализации изменение ожидаемого поведения всегда оформляй новой correction-спекой
по [correction-template.md](correction-template.md). Исправление кода до прежнего ожидаемого
поведения — bug со ссылкой на действующие AC, без переписывания требований.

Correction принадлежит одной исходной story, имеет новые AC и собственный цикл
Analysis → G2 → approve → реализация → ревью → QA. Несколько затронутых stories — несколько
связанных corrections. Цепочку `corrects` и `supersedes` оформляй по справочнику. Новую
самостоятельную функциональность вне scope исходной фичи оформляй новой master + story.

## AC и инженерные требования

- ID: `AC-F<F>-S<N>-01`; correction: `AC-F<F>-S<N>-C<K>-01`. Не переиспользуй ID.
- Один AC = один Given/When/Then с наблюдаемым результатом и `Проверка: stand|integration|unit`.
  Stand — API/UI, integration — consumer/job с реальными зависимостями, unit — чистые вычисления.
- Для API покрой успех, auth/RBAC, 404, невалидный ввод и границы применимых списков.
- Производительность числами: p95/p99, RPS, объём; согласованность и идемпотентность явно.
  Большие объёмы не грузятся целиком в память; решение работает в нескольких экземплярах.
- Загрузи `sdc`: общие ограничения в master, конкретные решения в story/correction.
- Новые ресурсы внеси в `docs/arch/ownership-map.md`, счётчики в `docs/arch/budget.md`.
  При достижении порога отметь необходимость ADR. Эти карты обновляются в анализе, одним
  владельцем; разработчики параллельных stories их не редактируют.
- React: сценарии/слайсы FSD, HTTP через shared/api или entities/<x>/api; Angular:
  feature-области и core-зависимости. Загрузи соответствующий skill.

## Перед передачей

Нет незаполненных маркеров; каждый FR покрыт; каждый исполняемый узел имеет собственные AC,
SDC или обоснованный N/A, границы записи и план QA. Ссылки разрешаются, DAG без циклов,
конкурирующие corrections отсутствуют. Старые утверждённые файлы не изменены.
