1. Одна схема, чтобы не путать технологии

Это не четыре взаимозаменяемые библиотеки. Каждая закрывает свой инженерный вопрос.

СлойВопросПрактический ответ
HarnessВ каких границах действует агент?Правила, права, sandbox, проверки, CI.
MCP / toolsЧто агент может узнать или сделать?Узкие действия: Jira, CI, draft PR.
ReActКак он решает итеративно?Reason → Action → Observation → следующий шаг.
RAGОткуда взять корпоративное знание?Релевантные ADR, wiki и стандарты в контекст.
LangGraphКак пережить долгий ветвящийся процесс?Состояние, чекпоинты, retries, ожидание CI и approval.
Короткое правило. Knowledge → AGENTS.md / RAG; Procedure → skill; External capability → MCP; Guarantee → hook / CI gate; long-running workflow → LangGraph.

2. Сценарий 1 — агент реализует REST endpoint

Задача: ANTIFRAUD-421. Добавить POST /api/v1/rules/{id}/activate; активировать можно только правило в DRAFT, нужен аудит и тесты.

Наблюдаемый ReAct-цикл

  1. Прочитать Jira.
  2. Найти RuleController, RuleService и похожий deactivate().
  3. Прочитать архитектурные ограничения.
  4. Реализовать переход состояния и audit event.
  5. Запустить тесты; увидеть отсутствие аудита.
  6. Исправить, запустить verify, посмотреть diff.

Почему без LangGraph

Один репозиторий, минуты работы, линейная задача, нет ожидания внешнего события. Достаточны coding agent, tools и жёсткий quality gate.

public RuleDto activate(UUID id, Actor actor) {
  Rule rule = ruleRepository.getRequired(id);
  rule.activate(); // допускает только DRAFT
  auditService.record("RULE_ACTIVATED", id, actor.id());
  return mapper.toDto(ruleRepository.save(rule));
}

3. Harness: агенту дают свободу, системе — право сказать «нет»

Контекст

AGENTS.md, ADR, API и security rules — что необходимо знать до действия.

Процедуры

Skills: повторяемые маршруты для API, миграций, bugfix и review.

Гарантии

Hooks и CI запускают проверки, а не просят их не забыть.

Минимальный AGENTS.md для Spring Boot сервиса

# Stack
Java 21 · Spring Boot · PostgreSQL · Kafka

# Architecture
Controller → ApplicationService → Domain → Infrastructure
Forbidden: Controller → Repository; Domain → Spring/JPA.

# Rules
- constructor injection only
- public API change requires integration tests
- DB changes only through Liquibase
- no production access; never push directly to main

# Definition of Done
./mvnw test
./mvnw verify
Never report DONE while a required check is failing.
Skill implement-rest-api
1) read OpenAPI and similar endpoint; 2) add validation; 3) implement application service; 4) unit + integration tests; 5) run verification; 6) include evidence.
Не полагайтесь на prompt.
«Запусти тесты» — пожелание. Pipeline, который запрещает merge при падении mvn verify, — гарантия.

Запускайте агента в devcontainer/Docker: внутри — репозиторий, JDK, Maven и тестовые сервисы; снаружи остаются SSH-ключи, production credentials и рабочая машина. Один task → один worktree → одна ветка → один PR.

4. MCP tools на Java: не «доступ к Jira», а точные возможности

MCP — контракт между агентом и внешней системой. Хороший tool узкий, проверяемый и имеет понятный эффект.

@Component
class JiraTools {
  private final JiraService jira;
  JiraTools(JiraService jira) { this.jira = jira; }

  @McpTool(description = "Get development task by issue key")
  JiraIssue getIssue(@McpToolParam(description = "e.g. ANTIFRAUD-421") String key) {
    return jira.getIssue(key);
  }

  @McpTool(description = "Add implementation summary to an issue")
  void addImplementationComment(String key, String summary) {
    jira.addComment(key, summary);
  }
}
РазрешатьНе давать по умолчаниюПричина
getIssue, getCiStatusrawRequest(url, method, body)Узкие действия проще валидировать, логировать и отзывать.
createDraftPrmerge / push to mainЧерновик обратим; merge требует approval.
read-only production signalsdestructive SQL / arbitrary production shellРазделяйте диагностику и изменение production.

5. Spring AI: tool-calling превращает LLM в рабочий цикл

В простом агенте Spring AI вызывает инструмент, возвращает результат модели и даёт ей выбрать следующий шаг. У application-кода остаются права, бизнес-правила и наблюдаемость.

class DevelopmentTools {
  @Tool(description = "Search source code")
  SearchResult searchCode(String query) { return repository.search(query); }

  @Tool(description = "Run Maven tests for a module")
  TestResult runTests(String module) { return build.runTests(module); }
}

String outcome = chatClient.prompt("""
  Implement ANTIFRAUD-421. Follow AGENTS.md.
  Add tests and do not finish while verification fails.
  """).tools(new DevelopmentTools()).call().content();
Важно: tool-calling не заменяет harness. Только независимый gate подтверждает, что тесты, архитектура и безопасность действительно проходят.

6. RAG с pgvector: доставить знание, а не 50 МБ документов

Когда у команды десятки сервисов, ADR, Confluence и стандартов, агенту нужен поиск по смыслу, а не огромный prompt.

CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE knowledge_chunk (
  id uuid primary key, source text, content text,
  embedding vector(1536), metadata jsonb
);
-- embedding(query) → top-k chunks → prompt + task
ЗапросДостаточный подход
«Найди наш стандарт Kafka retry»RAG / semantic search, агент не нужен.
«Добавь consumer по стандарту»RAG + tools + ReAct.
«Обнови consumer во всех сервисах и дождись CI»RAG + MCP + orchestration + checkpoints.

Качество RAG начинается с документов: версия, владелец, источник, access control, хороший chunking и eval-набор вопросов важнее выбора векторной БД.

7. Сценарий 2 — исправить CVE в 20 сервисах

Найдена уязвимость в foo-library 3.4; 20 сервисов надо обновить до 3.6, исправить несовместимости и открыть PR.

Когда нужна мультиагентность: репозитории независимы, есть значимый объём и агрегирование результата. Для обычной feature-задачи один агент обычно проще, дешевле и легче проверяется.

Контракт worker-а

  • Работает только в своём worktree и ветке.
  • Меняет только allowlisted dependency и совместимые участки кода.
  • Прикладывает build/test output, список изменений и открытые риски.
  • Не создаёт merge: reviewer и владелец репозитория принимают решение.

9. Сценарий 3 — расследование production incident

Alert: растёт 5xx у Payments. Агент помогает быстро собрать картину, но не имеет права менять production.

Разрешённый read-only путь

  1. MCP: получить alert, логи, traces, deploy history, dashboards.
  2. RAG: найти runbook, SLO и прошлые инциденты.
  3. ReAct: сформировать гипотезы, проверить сигналы, сузить причину.
  4. Собрать incident brief с уровнем уверенности и evidence.

Что остаётся человеку

  • rollback, feature flag, масштабирование;
  • изменение Kubernetes / БД;
  • коммуникация с клиентами;
  • решение о закрытии инцидента.

10. Code Review Agent и Evaluator → Optimizer

Reviewer получает diff, acceptance criteria и найденный контекст, но по умолчанию не меняет код. Он ищет конкретные проблемы: нарушение слоёв, авторизацию, миграции, null/transaction/concurrency, observability, тестовые пробелы.

{
  "verdict": "changes_requested",
  "findings": [{
    "severity": "high",
    "file": "RuleController.java",
    "evidence": "controller calls repository directly",
    "recommendation": "move lookup to RuleApplicationService"
  }],
  "positive_checks": ["activation audit is covered"]
}
Evaluator → Optimizer лучше, чем «сразу перепиши всё»: сначала независимая оценка по рубрике, затем ограниченное исправление подтверждённых findings, затем повторная оценка.

11. Quality gates и Evidence Bundle

Модель не объявляет код хорошим. Это делает независимый проверяемый конвейер.

Java quality gate

  • ./mvnw verify
  • JUnit + Testcontainers
  • ArchUnit
  • SpotBugs / Checkstyle
  • dependency & secret scan
  • SonarQube quality gate

Evidence Bundle в PR

  • issue и acceptance criteria;
  • изменённые файлы;
  • команды и статусы проверок;
  • coverage / scan summaries;
  • ссылки на CI и findings;
  • ограничения и ручные шаги.

12. Пошаговая стратегия внедрения для Java-команды

1
Сначала — детерминированная база.
Приведите в порядок mvn verify, тесты, ArchUnit, SAST/dependency scan и CI. Без честной обратной связи агент лишь быстрее создаёт долг.
2
Добавьте AGENTS.md и 3–5 skills.
Начните с REST API, bugfix, миграции БД и review. Правила должны быть короткими, конкретными и проверяемыми.
3
Запустите single-agent MVP.
Пять инструментов достаточно: read file, search code, edit, run tests/build, read Jira. Только отдельная ветка и draft PR.
4
Подключите RAG для живого знания.
Проиндексируйте ADR, API/security standards и runbooks. Оцените retrieval на реальных вопросах команды.
5
Вынесите внешние интеграции в MCP.
Начните read-only; write-capabilities добавляйте точечно, с audit log и approval boundary.
6
Измеряйте, а не верьте.
Соберите набор задач: endpoint, bugfix, migration, security finding, incident analysis. Меряйте pass rate gates, reviewer rework и опасные действия.
7
Только затем — orchestration.
LangGraph и workers оправданы для длинных, много-репозиторных, прерываемых процессов. Сначала докажите ценность на одном агенте.
Итоговый принцип: не нужно ожидать, что AI всегда напишет идеальный код. Нужно построить среду, в которой агент может быстро действовать, а система с высокой вероятностью не пропускает плохой или опасный результат.

Как читать этот документ, если вы только начинаете

Агентная разработка — это не попытка «посадить чат-бота за клавиатуру». Это способ встроить AI в инженерный процесс так, чтобы он ускорял работу, но не становился единственной точкой доверия.

Для начинающего инженера

Модель хорошо помогает искать, сравнивать, предлагать и выполнять рутинные шаги. Но она не знает, какие правила вашей компании важны именно сегодня, и может уверенно ошибаться. Поэтому ей нужны контекст, инструменты с ограничениями и проверка результата.

Для техлида

Смотрите на агента как на нового очень быстрого junior-инженера: он может прочитать много контекста и быстро сделать черновик, но его изменения должны проходить те же архитектурные, тестовые и security-барьеры, что и изменения человека.

Что именно меняется в привычном цикле разработки

Обычный процессПроцесс с агентомЧто остаётся неизменным
Инженер читает задачу, ищет похожий код и пишет реализацию.Агент собирает контекст и готовит реализацию; инженер направляет задачу и принимает решение.Требования, архитектура, code review и ответственность команды.
Инженер запускает проверки перед PR.Агент запускает их сам, получает ошибки и повторяет цикл исправления.Проверки должны быть воспроизводимы и независимы от модели.
Reviewer читает PR.Reviewer получает ещё и evidence bundle от агента.Merge не делегируется модели по умолчанию.
Практический ориентир на первые 2–4 недели. Не стройте автономную платформу. Возьмите один сервис, один тип задач, одну ветку, draft PR и обязательный mvn verify. Это уже даст реальный опыт и измеримые результаты.

Развёрнутый walkthrough: от Jira-задачи до безопасного PR

Ниже — тот же endpoint, но так, как его реально стоит провести в команде. Это показывает точки контроля, а не только «agent writes code».

1
Сформулировать задачу как контракт.
В Jira должны быть не только название и endpoint, но и допускаемые состояния, ошибка для недопустимого перехода, кто имеет право на операцию, audit-событие и минимум тестовых сценариев. Если этого нет, агент должен задать вопрос или пометить неопределённость, а не угадать правило.
2
Дать агенту ровно нужный контекст.
Он читает ticket, AGENTS.md, OpenAPI и 1–2 похожие операции. Не надо загружать весь монорепозиторий или все Confluence-страницы в prompt: это добавляет шум и ухудшает выбор.
3
Попросить сначала составить план.
«Назови файлы, которые собираешься менять, и тесты, которые добавишь; не редактируй до плана». Это дешёвая точка, где техлид может заметить неверное понимание до появления большого diff.
4
Реализация в границах архитектуры.
Controller только валидирует HTTP-запрос и вызывает application service. Application service управляет транзакцией и аудитом. Domain решает, разрешён ли переход DRAFT → ACTIVE. Это правило нужно дать явно, иначе агент выберет самый короткий путь — вызвать repository из controller.
5
Проверка и корректировка.
Агент запускает узкие тесты, затем ./mvnw verify. Если ArchUnit сообщает о зависимости domain от JPA, агент исправляет именно это нарушение и повторяет gate. Не «додумывает», что ошибка не важна.
6
Draft PR, а не готовый merge.
В описании PR агент указывает, что изменил, какие критерии закрыты, какие команды проходили и какие есть риски. Человек всё равно проверяет смысл бизнес-решения.

Пример хорошей постановки для агента

Реализуй ANTIFRAUD-421 в отдельной ветке.
До изменений: прочитай AGENTS.md, OpenAPI и аналог deactivate().
Сначала предложи краткий план с файлами и тестовыми случаями.

Acceptance criteria:
1. POST /api/v1/rules/{id}/activate доступен роли RULE_ADMIN.
2. Только DRAFT может перейти в ACTIVE; иначе вернуть 409.
3. При успехе записывается RULE_ACTIVATED с actor и rule id.
4. Есть unit-тест transition и integration-тест endpoint.
5. Заверши только после ./mvnw verify; приложи результат в draft PR.

Не меняй production-конфигурацию, не отключай тесты, не выполняй merge.

Что должен проверить человек в PR

  • Правильно ли понято бизнес-правило, особенно статусы и права доступа.
  • Не появился ли обход архитектурного слоя ради более короткой реализации.
  • Тестируют ли тесты поведение, а не детали реализации.
  • Нет ли случайных изменений в несвязанных файлах.
  • Достаточна ли audit-запись для расследования будущих инцидентов.

Как выбрать технологию без overengineering

Самая частая ошибка — начинать со сложного multi-agent графа. Начинайте с минимального механизма, который даёт проверяемую пользу.

RAG на практике: почему «загрузить Confluence» недостаточно

RAG — не память модели, а управляемый поиск: перед ответом или действием система извлекает несколько фрагментов знаний и явно добавляет их в контекст. Команда может обновить правило без переобучения модели.

Хороший первый корпус

  • актуальные ADR с владельцем и датой;
  • API, DB, logging и security guidelines;
  • runbooks и SLO для incident response;
  • README сервисов и примеры типовых решений.

Чего не делать

  • не смешивать устаревшие и актуальные политики без метаданных;
  • не индексировать секреты, PII и закрытые incident reports без ACL;
  • не считать top-5 найденных кусочков доказанной истиной.

Поток данных, который стоит обсудить с владельцами знаний

  1. Ingestion. Забираем только одобренные источники и фиксируем источник, версию, дату и access label.
  2. Chunking. Делим по смысловым секциям: один ADR decision, один подраздел runbook, одно API rule.
  3. Retrieval. Выбираем 3–8 фрагментов с фильтрами по системе, версии и правам пользователя.
  4. Grounded response. Агент отвечает с названием источника и помечает отсутствие данных вместо выдумывания правила.
  5. Evaluation. Храним 20–50 реальных вопросов и проверяем, найден ли правильный документ и не подмешался ли старый стандарт.

MCP на практике: проектирование capability, а не API-клиента

Добавляя tool, вы фактически выдаёте агенту полномочие. Описание, параметры, авторизация, rate limit и audit log — часть безопасности, а не техническая мелочь.

ВместоСделайтеПольза
run_sql(query)getFailedPayments(from,to) с лимитом и read-only roleМеньше риска утечки и destructive query.
github_request(...)getPrDiff, createDraftPr, getChecksПонятные действия и понятный журнал.
kubectl(command)getPodLogs, getDeploymentHistoryДиагностика без привилегии менять production.

Чек-лист для каждого tool

  • Может ли он быть read-only? Если нет — можно ли сделать draft/preview режим?
  • Какой минимальный input нужен? Валидируются ли ID, path и лимиты?
  • Какие данные вернутся в контекст модели; не окажутся ли там токены, PII или секреты?
  • Кто может вызвать capability и как это будет записано в audit log?
  • Нужен ли explicit confirmation прямо перед вызовом?

Операционная модель: роли, метрики и безопасные границы

Инженер

Техлид / platform

Поддерживает AGENTS.md, skills, quality gates, инструментальные права и eval-набор.

Security / SRE

Утверждает production boundaries, доступы к MCP и сценарии incident response.
